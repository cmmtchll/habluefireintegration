# J1708 startup and read actions

[Home](../README.md) · [Setup](getting-started.md) · [Diagnostics](diagnostics.md)

J1708 is the data link; J1587 defines the MID/PID application data. Incoming
decoding, adapter initialization, and active parameter requests are separate
concerns. This guide describes the opt-in **unsecured EZ** startup path, not
support for secured adapters or a claim of vehicle compatibility.

## Enable startup

In **Settings → Devices & services → BlueFire → Reconfigure**:

1. Select the adapter's **J1587 adapter firmware format**. Firmware **3.23.0**
   uses **Extended (3.19+)**.
2. Enable **Enable J1708 startup (unsecured EZ adapters)**.
3. Save to reload the entry.

The same settings are available during initial setup. Existing entries remain
receive-only until startup is enabled. A firmware-format selection by itself
does not enable writes, and an application version is not an adapter firmware
format selector.

The integration does not change bus-ignore flags, sleep/LED variables, security,
or firmware. Firmware **4.2.3 is not installed** by this integration; an upgrade
is not required to exercise the 3.23.0 path. Secured adapters are rejected without
alternate credentials or security resets.

## What startup does

The receiver waits for a heartbeat, negotiates firmware/client compatibility,
checks unsecured authentication, reads adapter variables and J1708 availability,
signals application connection, installs passive subscriptions, and starts
reports. Telemetry received before successful startup is discarded.

Firmware 3.x checks two authentication responses. Unversioned EZ advertisements
take the 3.x version-query path; a version-bearing 4.x advertisement uses a
different startup layout. The inspected compatibility tuple `12.5.6` describes
the wire profile, not this integration's version; platform 0 is unspecified.
Firmware 3.23.0 is the primary synthetic startup fixture.

Client packets are at most 20 bytes and use write-with-response on EZ `ca101`.
Malformed/rejected replies, firmware-format mismatches, explicitly disabled
J1708, and missing replies fail explicitly. Each exchange has a 10-second
deadline, followed by normal reconnect backoff. Authentication and subscriptions
are rebuilt on every connection, including after an exclusive inspection.

An initial **unavailable** J1708 response is preserved in diagnostics and logged,
but does not prevent authenticated passive initialization. This follows the
observed vendor behavior; the status is not proof that telemetry will follow.
`ready` means the report-start exchange completed, not that an ECU has supplied
a measurement.

### Passive subscriptions

There are **48 subscriptions**, each using wildcard MID 0 and a 1000 ms monitor
interval:

| Group | Subscriptions |
| --- | --- |
| Numeric measurements | 39 supported PIDs |
| Status | Retarder/parking switches, cruise status, selected/current gear |
| Diagnostics | PID 194 |
| Identification | PIDs 234, 237, 243 |

Vendor subscription MID 0 means any MID. Actual responding controllers retain
their own identities. Sensors are discovered only when a supported report
arrives; subscription support does not establish that the ECU broadcasts it.
The expanded filter set and adapter filter capacity still need hardware
confirmation. An explicit subscription rejection remains a startup error.

## Automatic one-minute reads

After startup reaches `ready`, the receiver actively requests these five PIDs:

| PID | Reading | Output |
| --- | --- | --- |
| 96 | Fuel level | % |
| 194 | Diagnostic codes | Reported active/inactive faults |
| 245 | Odometer | km |
| 247 | Total engine hours | h |
| 250 | Total fuel used | L, not fuel remaining |

The first round starts one minute after startup. Reads run sequentially, each
collecting reports for five seconds before restoring passive monitoring.
Normal collection does not shift the minute cadence. If a round takes longer
than a minute, the next round waits another minute; there are no catch-up bursts.

Failures back off independently per PID: **2, 4, 8, then at most 15 minutes**.
A successful read restores that PID's one-minute cadence. Errors are logged and
counted, never converted to zero fuel or empty fault lists. Missing fuel does
not suppress diagnostic reads. Polling skips a PID while a manual read is active.

Polling and liveness-probe writes are serialized. Unload/shutdown, inspection,
and standalone capture cancel the session tasks; reconnect starts a fresh
schedule. Diagnostic downloads observe the live session without pausing it.
Receive-only entries do not poll.

This is a selected poll list, **not** an inventory of request-only measurements.
Broadcast/request behavior is controller-specific. The inspected vendor client
has an odometer-request setting, but distance, hours, and total fuel have not
been established as request-only on this ECU.

### Freshness with polling

Fuel level and diagnostic-code live sensors expire after **180 seconds**
without their own reports. J1587 protocol availability also uses a 180-second
grace period while polling is enabled. Other live sensors retain 60-second
expiry; disconnect withdraws live availability immediately.

Distance, hours, and cumulative fuel/idle totals are retained last-known
`total_increasing` counters with observation timestamps, not expiring live
readings. Failed polls and unavailable samples do not replace a valid retained
total. See the complete [retention and availability rules](mqtt.md#delivery-and-freshness).

## Manual read actions

Use **Developer tools → Actions** and select the BlueFire config entry.
All reads require a connected, ready, opt-in J1708 startup session.

| Action | PID | Result |
| --- | --- | --- |
| `bluefire.read_fuel_level` | 96 | Fuel percent per responding MID |
| `bluefire.read_diagnostic_codes` | 194 | Active/inactive fault entries per MID |
| `bluefire.read_odometer` | 245 | Total distance in km |
| `bluefire.read_engine_hours` | 247 | Total engine hours in h |
| `bluefire.read_total_fuel_used` | 250 | Total fuel used in L |
| `bluefire.read_software_identification` | 234 | Controller-reported software text |
| `bluefire.read_vehicle_identification` | 237 | Identification text, not automatically a valid VIN |
| `bluefire.read_component_identification` | 243 | Component make/model/serial text, where reported |
| `bluefire.read_parameter` | Allowlisted `pid` | Supported measurement/status/identity/fault data, or raw PID 174 |

Every read accepts optional `mid`: **128** conventionally targets the engine,
**130** the transmission; omit it or use **0** for all responding controllers.
Other valid targets are 128–255. The target filters returned reports, not
unrelated passive telemetry.

```yaml
action: bluefire.read_parameter
data:
  entry_id: YOUR_BLUEFIRE_ENTRY_ID
  mid: 128
  pid: 439
response_variable: boost_report
```

Useful manual PIDs include fan speed **26**, engine torque factor **68**,
retarder torque **122**, cruise status/set speed **85/86**, parking brake **70**,
selected/current gear **162/163**, fuel economy **184/185**, idle hours/fuel
**235/236**, and extended boost **439**. The
[generated allowlist](code-reference.md#j1587-status-and-read-only-request-support)
is authoritative. PID **174** fuel temperature is raw-only because its scale
is not established. Arbitrary requests, fault-clearing PIDs 195/196, programming,
and actuator commands are rejected. Additional manual reads do not expand the
five-PID poll set.

### Responses and errors

A read sends one one-shot vehicle-bus request, collects for five seconds, then
restores the normal passive subscription. Concurrent reads are rejected.
Disconnects and write failures surface as action errors; failure to restore
monitoring forces reconnect before another read.

Matching reports update existing MQTT sensors and appear in the action response
as `pid` plus `reports`, sorted by `mid`. Multiple reports from one MID keep its
latest report. Numeric reports contain `signals` with values and units;
diagnostic reports contain `diagnostics` with fault entries, active flags,
PID/SID, FMI, optional occurrence counts, and available descriptions.
All-ones numeric values remain null.

**No response is an error, not zero fuel, no faults, or proof of an absent
sensor.** Only an actual empty PID 194 report means no faults in that
controller's report, not vehicle-wide health. PIDData has no transaction ID,
so the collection window may include broadcasts rather than only
request-triggered responses.

There is no tank-capacity setting or litres/gallons-remaining calculation.
Reads are J1708-only; passive J1939 fuel/fault decoding is unchanged.

The wire evidence is Windows 12.5.6 `CommData.AddPID`: command 155, selected MID,
big-endian 16-bit PID, `OnRequest=1`, `OnceOnly=1`, zero interval, trailing zero.
Restoration uses `OnRequest=0`, `OnInterval=2`, 1000 ms monitoring. See
[package provenance](protocol-investigation.md#package-provenance).
This is static evidence plus synthetic coverage, not vehicle commissioning.

## Controller identification

Startup sends one active read each for **234, 237, and 243** after authenticated
report setup. They run once per connection, including reconnect after inspection,
not in the minute polling loop. Missing identification responses do not block
telemetry or cause retries; BLE write failures and adapter rejection still fail.
Receive-only mode sends no reads.

Printable ASCII is exposed with surrounding spaces removed and field separators
preserved. There is no make/model splitting, calibration inference, automatic
controller-generation inference, or fault-profile selection. Empty/blank/all-ones
responses are `unavailable`; other encodings are `unsupported_encoding` with a
null value. Raw hex is retained. `identity_basis: controller_reported` describes
provenance, not verified ECU identity.

For vendor PID 243 responses that prefix the text with the MID, the vendor
boundary validates/removes the wrapper before ASCII decoding. Normalized reports
and raw J1708 datagrams keep their separate contracts.

Identification appears in three places:

| Surface | Behavior |
| --- | --- |
| MQTT | Diagnostic text at `vehicle/{vehicle}/j1587/{mid}/pid/{234\|237\|243}`; retained QoS 1 and replayed on birth/reconnect |
| Native BlueFire sensors | Created only for received identities; stable config-entry/MID/PID IDs, independent of MQTT publication |
| Downloaded diagnostics | `bridge.j1587.controller_identification`; startup also records `identification_requests_sent` |

Valid identities are cached locally per entry and vehicle, restored after an HA
restart, and shown as last-observed information without asserting availability.
Reconnect reuses entities. Missing, unavailable, or unsupported responses never
overwrite a previously decoded identity; a new valid response refreshes it.
The BlueFire device's manufacturer/model is not replaced by ECU text.

Changing discovery prefix preserves identity; changing vehicle identity starts
a fresh cache. Entry removal deletes the cache and queues retained-state cleanup.
An unsupported ECU creates no identification sensors. Long responses requiring
PID 192 multisection assembly remain unsupported unless the adapter supplies a
complete normalized report. Text may contain VINs and serial numbers.

## Adapter liveness

After startup, a read-only **Get J1708 availability** (command 7) runs every
10 seconds. This experimental adapter-level probe is not authentication, a
settings change, or an active vehicle-bus request. Both available and unavailable
replies prove adapter responsiveness, but neither marks telemetry online.

A missing reply times out after 10 seconds and is logged/counted, without an
immediate disconnect. A successful reply resets consecutive misses. Three
consecutive misses trigger reconnect only when no checksum-valid traffic has
arrived within 30 seconds. Heartbeats and reports prove transport liveness even
if a probe reply is lost; only valid telemetry establishes data availability.
Malformed replies and BLE write failures still trigger reconnect.

Probes run independently of MQTT, stop before disconnect, and are disabled in
receive-only mode. A successful session resets reconnect backoff.
Whether this probe prevents physical adapter dropouts still needs hardware
verification. Classic outgoing command-255 heartbeat timers are not evidence
of an EZ BLE requirement; see [protocol findings](protocol-investigation.md).
